# MarketProfileBuilder v2

`market_profile_builder_v2.py` — отдельный упрощённый builder. Старые
`synthetic_vacancy_pipeline.py` и `research_market_profile_builder.py` сохраняют
свои алгоритмы. Общая схема из `market_profile.py`
расширена необязательными полями; старые сохранённые профили читаются.

## Pipeline

```text
TargetProfile
→ 3–6 простых query
→ существующие providers
→ удаление копий по ID, URL и полному тексту объявления
→ lexical + alias + bge-m3 ranking
→ relevance validation порциями по 20: direct / adjacent / irrelevant
→ normalization и добор после исключений
→ две отдельные выборки: direct / adjacent
→ объединение эквивалентных требований внутри каждой выборки
→ MarketProfile по direct + необязательный adjacent_context
```

Lexical и embedding similarity определяют порядок рассмотрения, но не являются
hard gates. Semantic-only вакансия может дойти до relevance validation.
`irrelevant` в market sample не попадает. Только direct формирует основные
требования, частоты и сравнение с резюме. До шести adjacent сохраняются в
`adjacent_context` со своими частотами и источниками. Этот контекст показывается
в отчёте как материал для изучения возможных направлений развития.

Для основной выборки требуется 3–6 direct. Смежные вакансии не восполняют
недостающие прямые совпадения, но их контекст сохраняется даже при
`insufficient_market_data`.

После extraction дополнительно проверяется структурированный seniority из
полного описания. Если для цели Middle normalization обнаружила Senior/Lead/
Staff/Principal/Head, вакансия исключается и сохраняется в diagnostics как
`post_normalization_rejections`. Статусы extraction `failed`, `empty`, `sparse`
и отсутствие результата тоже исключают карточку. Builder берёт следующие
прямые вакансии по рейтингу и, если нужно, проверяет следующую порцию
кандидатов. Добор заканчивается при достижении sample_limit или исчерпании
найденного пула (до 80 карточек). `candidate_limit` — размер порции, а не
ограничение всего резерва.

Builder принимает только целевую профессию. `core_skills` очищается до поиска,
поэтому навыки конкретного кандидата не меняют рыночный профиль.

## Совместимость и маленькая выборка

Общая схема `MarketProfile` допускает 3–6 вакансий и confidence
`low/medium/high`. Старые профили с `medium/high` продолжают читаться:

- 0–1 прямая вакансия — `insufficient_market_data`;
- 2 прямые вакансии — `insufficient_market_data`, но обе сохраняются как отдельный
  предварительный рыночный сигнал в sources, summary и diagnostics;
- 3–6 прямых вакансий с повторяющимися требованиями — совместимый `MarketProfile`.

Confidence сохраняется без повышения: `MarketProfile` → сравнение → рекомендации
→ итоговый JSON и Markdown. При `low` профиль с повторяющимися требованиями
остаётся полезным, но советы явно обозначаются как предварительные.

`market_reliability.py` формирует `reliability`: количество независимых
работодателей, известных работодателей, прямых совпадений, подтверждённых полных
описаний, свежих дат публикации и площадок. Сохраняются дата оценки, период
120 дней, количество удалённых копий и причины уровня уверенности.

- `high`: шесть прямых вакансий, минимум четыре независимых работодателя и
  две площадки; для всех подтверждены работодатель, полнота, свежесть и
  надёжная проверка профессии; доступны смысловое ранжирование и проверка содержания.
- `medium`: минимум пять прямых вакансий и три работодателя с теми же
  подтверждёнными данными, но не все условия `high` выполнены.
- `low`: небольшая выборка, недостаточная независимость или неподтверждённые
  данные, низкая уверенность проверки профессии либо недоступность моделей.

Это объяснимые пороги качества доступной выборки, а не статистическая
вероятность соответствия всему рынку. Неизвестные даты и полнота не считаются
подтверждёнными. Несколько названий компании связываются по её ID внутри
площадки; совпадающие нормализованные названия связывают работодателя между
площадками. ID разных площадок сами по себе не доказывают тождество компании.

Повтор карточки определяется по ID площадки, URL без tracking-параметров либо
одинаковым работодателю, названию и описанию на разных площадках. Отличающиеся
объявления одной компании сохраняются. Неизвестный работодатель и разные
подтверждённые регионы не позволяют объединить карточки только по тексту.
Копии с изменёнными формулировками могут потребовать ручной проверки.

При замене карточки более полной версией обновляется индекс описаний. Группа
копий сохраняет все известные площадки и регионы: смена представителя не
объединяет разные объявления исходной площадки или разных регионов. Ссылки
на итоговую карточку разрешаются внутри группы даже при одинаковых локальных
ID на разных площадках. Обычный поиск v2 получает карточки до старого
объединения по одному названию и работодателю; предел 80 применяется после
удаления копий. Правила поиска v1 сохраняются.

Старый сохранённый v2-профиль, где `low` ранее стал `medium`, при загрузке в
кандидатский pipeline понижается по соседнему `*.diagnostics.json`, если
совпадают цель и источники. Чужая диагностика не применяется. Старые профили
без этих метаданных сохраняют заявленный уровень; для новой оценки качества
выборки требуется заново построить профиль.

## Эквивалентные требования

`requirement_equivalence.py` объединяет морфологические формы и явные синонимы,
включая переводы: «анализ журналов», «анализ логов» и `log analysis` считаются
одной компетенцией. Для остальных перефразирований LLM может предложить группы
существующих требований. Python проверяет ссылки на группы, разделение
категорий, отсутствие повторного использования, различия известных технологий,
действий, отрицаний и числовых ограничений. Неизвестные названия инструментов
объединяются только по словарю или морфологии, без свободной догадки модели.

Названием остаётся одна исходная формулировка. `source_values` хранит все формы,
`evidence` связывает каждую форму из нормализованной карточки с `source_id`,
а `sources` содержит ссылки на объявления. Оригинальные полные описания
российских объявлений находятся в `*.collection.json`. Частота считается по
уникальным вакансиям: три синонима в одной карточке дают одно наблюдение.
«Python» и «анализ данных», «SQL» и «PostgreSQL» остаются разными требованиями.

Сравнение с резюме использует название и сохранённые эквивалентные формы.
При ошибке LLM остаётся детерминированное объединение. Для проверки сохраняются
`*.direct_concepts.json` и `*.adjacent_concepts.json`: состав групп, способ
объединения и отклонённые предложения. Смысловая эквивалентность неизвестных
формулировок зависит от решения модели и этих ограничений.

Образование, инструменты и гибкие навыки объединяются только по явным
эквивалентам и морфологии. Разные уровни образования и специальности остаются
раздельными. Для профессиональных навыков и обязанностей предложение модели
принимается только при совпадении проверяемых действия и объекта; неизвестные
конструкции сохраняются отдельно.

Готовый профиль можно пересчитать по сохранённому normalization cache, без
поиска и новых вызовов модели:

```powershell
python -m scripts.reaggregate_market_profile output/candidate/.stages/market_profile.json
```

Пересчёт сохраняет исходный состав основной и смежной выборок и использует
только детерминированные эквиваленты. Затем отчёт можно пересобрать через
`candidate_assessment_pipeline` с `--market-profile` и `--resume-evaluation`.

## Отказоустойчивость

- Ошибка одного provider сохраняется в diagnostics и не останавливает поиск.
- Если `bge-m3` недоступна, используется lexical/alias ranking.
- Если Gemma недоступна, допускаются только сильные объяснимые title/alias
  совпадения, а sampling-confidence снижается.
- Ошибка normalization отдельной вакансии не отменяет остальные.
- `*.diagnostics.json` содержит `backfill_count`, `normalization_rounds`,
  `normalization_candidates` и исключения. Общий normalization checkpoint
  содержит ссылки на отдельные файлы каждого раунда, сохраняя причины ошибок.
- Cache и checkpoint используют namespace `market_profile_v2` и не смешиваются
  с v1.

## Запуск

```powershell
python -m resume_evaluator.market_profile_builder_v2 "Middle ML Engineer"
```

Python API:

```python
from resume_evaluator.market_profile_builder_v2 import build_market_profile_v2

profile = build_market_profile_v2(target_profile)
```

Opt-in в едином кандидатском pipeline:

```powershell
python -m resume_evaluator.candidate_assessment_pipeline `
  resume.json "Middle ML Engineer" output/candidate_report_v2 `
  --market-v2
```

С ручной целевой должностью без `--market-v2` используется builder v1.
В сценарии России с должностью из резюме v2 применяется автоматически.
