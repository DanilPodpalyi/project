# Архитектура и контракты

Основной оркестратор — `candidate_assessment_pipeline.run_candidate_assessment`.
CLI `analyze` по умолчанию выбирает российский сценарий по желаемой должности.

1. `document_reader` читает TXT/DOCX/PDF; `resume_extractor` получает `ResumeData`.
2. `resume_quality_evaluator` получает оценки разделов модели, проверяет их
   и суммирует в Python. Это качество документа, а не процент совпадения с рынком.
3. `russian_market` получает должность, явно указанный уровень, собирает полные
   описания и проверяет страну/дату. `bilingual_titles` и `title_morphology` расширяют поиск.
4. `market_profile_builder_v2` проверяет содержательную релевантность, отделяет
   смежные вакансии и строит частоты. `market_reliability` оценивает основания уверенности.
5. `candidate_market_comparison` ищет практические доказательства и упоминания;
   `requirement_equivalence` защищает объединение требований разных типов.
6. `recommendation_generator` получает готовые факты, а не самостоятельно ищет рынок;
   при сбое LLM использует ограниченные шаблоны. Оркестратор сохраняет отчёт.

`market_profile.py` содержит общие Pydantic-контракты, извлечение, embeddings
и совместимый builder v1. Из-за общих функций этот модуль необходим основному сценарию.
`legacy/` содержит старое сравнение с одной вакансией и исторические алгоритмы;
`research/` — исследовательскую копию. Старые модули в корне пакета перенаправляют
импорт к новым реализациям и сохраняют прежние команды `python -m <module>`.
Общие утилиты чтения, настройки и atomic write используются во всех сценариях.

## Выходной контракт

`CandidateReport` (`candidate_assessment_pipeline.py`) валидирует итоговый JSON:
`status` (`ok`/`partial`), `run_id`, `target`, `resume_evaluation`, `market_context`,
`market_comparison`, `recommendations`, `artifacts`, время этапов.
Пути внутри `artifacts` относительны папке отчёта. Ссылки и исходные формулировки
требований находятся в JSON; краткий Markdown ограничивает повторение деталей.

`market_context.collection_errors` показывает проблемы источников,
`search_warnings` — ограничения поиска. `partial` допустим, когда данных
недостаточно для основного профиля. Смежная выборка не добавляется к его частотам.
`evidenced`, `mentioned_only`, `not_found` описывают текст резюме, а не фактический
уровень владения кандидатом. Практические доказательства нужны из задач/опыта/результатов.

`run.json` имеет `schema_version=1`, версию приложения, идентификатор, входные
SHA-256, настройки, этап, `status` (`running`/`completed`/`failed`/`interrupted`).
У завершённого основного запуска также есть `report_status` и SHA-256 отчёта.
Диагностика ошибки хранит тип, а не потенциально чувствительный текст ValidationError.

## Сохранение и кеши

`runtime.managed_run` резервирует папку через эксклюзивный `.run.lock`.
При наличии предыдущих результатов или lock создаётся новая подпапка.
Атомарная запись заменяет файл только после полной записи временного файла.
Чужой lock не удаляется. Жёсткое завершение процесса может оставить временные файлы;
последующие запуски не используют их как готовые артефакты.

Кеш HTTP учитывает время получения, URL и срок жизни. Кеш релевантности учитывает
цель, текст, модель и хеш промпта; нормализация — также версию алгоритма.
Кеш перевода учитывает должность, модель и версию. Локальные кеши не поставляются.
Результаты повторного запуска не продолжаются автоматически и не переиспользуются
неявно между разными папками. Готовые артефакты подключаются явными параметрами.

Ограничения: маленькая наблюдаемая выборка, изменчивые API и генерация LLM;
отсутствие OCR и автоматического возобновления; большие исторические общие модули.
Одинаковое имя модели не фиксирует её веса: окружение приёмки должно сохранять
`ollama list`/digest моделей отдельно. Пакет не включает сервер или веса.
