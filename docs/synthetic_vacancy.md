> Совместимый legacy-сценарий. Основная команда релиза: `python -m resume_evaluator analyze ...`; этот документ описывает прежний модуль.

# Синтетическая эталонная вакансия

Модуль `synthetic_vacancy_pipeline.py` строит эталонную вакансию по
структурированному резюме. Результат совместим со схемой `VacancyData` и может
передаваться непосредственно в `candidate_scorer.py`.

## Запуск

Сначала извлеките резюме:

```powershell
python -m resume_evaluator.resume_extractor `
  examples/resumes/anna_sokolova.docx `
  output/resume.json
```

Затем постройте эталонную вакансию:

```powershell
python -m resume_evaluator.synthetic_vacancy_pipeline `
  output/resume.json
```

По умолчанию результат сохраняется в `synthetic_vacancy.json`. Другой путь
можно передать вторым позиционным аргументом.

```powershell
python -m resume_evaluator.synthetic_vacancy_pipeline `
  output/resume.json `
  output/synthetic_vacancy.json
```

## Этапы

1. По резюме берутся только целевые `role`, `specialization`, `domain` и
   `seniority`. Навыки и опыт кандидата не влияют на поиск или релевантность
   рыночных вакансий. Модель дополняет универсальный `TargetProfile` полями
   `role_family`, `focus`, `aliases`, `adjacent_specializations` и
   `excluded_specializations`. До восьми запросов динамически строятся из
   specialization, aliases, seniority и domain. Приоритет получают точные
   варианты `"<name>" vacancy` / `"<name>" job`; API без phrase operators
   получают адаптированную чистую фразу. Отдельных шаблонов для конкретных
   профессий нет.
2. Публичные API Jobicy, JobsCollider, Remote OK, Remotive, Arbeitnow и hh.ru
   возвращают актуальные вакансии. Ошибка одного источника не останавливает
   остальные; после получения достаточного пула лишние запросы не выполняются.
3. Pipeline требует не менее 20 уникальных актуальных вакансий, удаляет
   дубликаты по URL и паре «название + работодатель».
4. Дешёвый локальный фильтр до embeddings отдельно считает для title точное
   совпадение specialization/alias, normalized phrase match, token overlap и
   fuzzy lexical similarity. `excluded_specializations` дают жёсткий reject,
   `adjacent_specializations` остаются кандидатами со штрафом. Источники с
   низкой title precision получают меньший вес только в рамках текущего запуска.
5. `bge-m3` добавляет dense semantic similarity к `title_match_score`, но не
   служит самостоятельным доказательством профессии: высокий cosine без
   лексического подтверждения помечается `semantic_only` и отклоняется. Затем
   сохраняется прежний hard gate `domain_similarity`; после hybrid ranking
   остаётся до 16 кандидатов. Для спорных TOP-кандидатов предусмотрен интерфейс
   лёгкого reranker и benchmark harness, но отдельная модель по умолчанию не
   подключена.
6. Сначала на полную нормализацию в Gemma отправляются 8 вакансий. Если market
   sample ещё меньше шести, добавляются следующие партии по 4 до общего лимита
   16. Процесс останавливается при шести качественных вакансиях или исчерпании
   пула.
   Перед вызовом проверяется `vacancy_normalization_cache.json`: ключом служит
   SHA-256 заголовка и полного текста вакансии. При совпадении хеша сохранённая
   нормализация используется повторно, даже если изменился `source_id`.
   Для новых текстов модель извлекает факты, добавляет структуру `profession`
   и помечает нерелевантные записи. Требования сохраняются раздельно в
   `professional_skills`, `tools_and_technologies`, `soft_skills`,
   `education_requirements` и `domain_knowledge`; обязанности остаются в
   `responsibilities`. Soft skills и образование не участвуют в статистике
   профессиональных навыков.
7. До выбора тройки универсально проверяются seniority, specialization,
   role_family, domain и focus. Более высокий явно указанный seniority
   исключается, неизвестный допускается с небольшим снижением score. Alias
   считается эквивалентом, смежное название требует semantic similarity не
   ниже `0.72`, а явно исключённое направление не входит в market sample.
   Python-код
   перебирает оставшиеся тройки. `triplet_score` состоит из средней
   релевантности профессии (40%), совпадения домена с целевым профилем (30%) и
   средней попарной cosine similarity embedding-векторов `title + short
   description` (30%). Проверяются как итоговый score, так и каждый компонент
   отдельно.
8. Python через `Counter` считает навыки по числу разных вакансий, вычисляет
   медиану опыта и объединяет образование, занятость, формат работы и условия.
   Gemma получает только обязанности: она объединяет семантически одинаковые
   действия и даёт группе краткую итоговую формулировку. Код отклоняет
   выдуманные элементы `members` и восстанавливает пропущенные исходные пункты.

Тот же профиль можно построить программно из прямого пользовательского запроса:

```python
from resume_evaluator.synthetic_vacancy_pipeline import build_target_profile

plan = build_target_profile("Корреспондент")
```

`plan.profession` содержит классификацию рынка, а `plan.search_queries` —
динамически сформированные запросы. Навыки пользователя в этот вызов не входят.

Частоты навыков считаются по market sample из 3–6 релевантных нормализованных
вакансий, а не только по финальной тройке. В `required_skills` попадают навыки
с покрытием не менее `ceil(2N/3)`; встречающиеся минимум дважды, но ниже этого
порога, попадают в `preferred_skills`.
Единичные навыки сохраняются отдельно в `market_variations` и не участвуют в
оценке кандидата. Опыт рассчитывается как медиана явно указанных минимальных
значений. Обязанности и условия сохраняются только при наличии одной смысловой
группы или одинакового нормализованного значения минимум в двух выбранных
вакансиях. После LLM-группировки Python дополнительно требует совпадения
действия и объекта обязанности и считает только разные вакансии. Таким образом,
LLM не определяет частоты, обязательность навыков, опыт, образование или другие
структурированные поля.

После нормализации Python присваивает каждой вакансии `extraction_status`:
`ok`, `empty`, `sparse` или `failed`. `empty` означает, что в исходном тексте
не обнаружен раздел профессиональных требований; `failed` — что признаки требований
есть, но извлечение вернуло пустой результат; `sparse` — подозрительно малое
число извлечённых пунктов. Для `failed` и `sparse` выполняется одна повторная
попытка извлечения. Если она не улучшила результат, такая вакансия не входит в
market sample и не считается доказательством отсутствия навыка на рынке.

## Проверяемость результата

Расширенные поля не мешают `VacancyData` и `candidate_scorer.py`:

- `selected_vacancies` — выбранные три вакансии и их ссылки;
- `requirement_evidence` — частота, ссылки и исходные варианты навыка;
- `market_variations` — единичные рыночные навыки, исключённые из скоринга;
- `market_vacancy_count` — размер выборки для частот навыков;
- `responsibility_evidence` — доказательства повторяющихся обязанностей;
- `experience_evidence` — значения опыта и ссылки;
- `other_requirement_evidence` — частоты и ссылки для медианного опыта,
  образования, занятости, формата работы и условий;
- `pipeline_statistics` — запросы, количества и ошибки источников.

В `pipeline_statistics.vacancies_after_prefilter` сохраняется фактическое
количество вакансий после дешёвого фильтра, а в
`vacancies_after_embedding_filter` — размер TOP после embeddings. Поле
`vacancies_selected_for_normalization` показывает, сколько вакансий из него
передано в нормализацию; значение не превышает 16.

Каждый запуск также сохраняет sidecar
`<output-stem>.retrieval_diagnostics.json`. В нём для каждого кандидата после
prefilter записаны exact/phrase/token/fuzzy/dense сигналы, `title_match_score`,
`semantic_only`, источник, запрос, domain/embedding scores и точная причина
отказа. Отдельно сохраняются Precision@10/20 по строгой нормализации,
hybrid-acceptance и conditional validated precision, распределения scores,
динамическая precision/error/timeout статистика каждого источника, размер
market sample и полное время.
Этот файл предназначен для диагностики retrieval и не используется при
агрегации или скоринге кандидата.

Cache хранится рядом с итоговым JSON в файле
`vacancy_normalization_cache.json`. В отличие от checkpoint, он предназначен
для повторного использования между завершёнными запусками. Версия cache и
checkpoint проверяется перед чтением, поэтому нормализация со старой или
несовместимой схемой не используется как актуальная.

## Confidence и отказ от генерации

Успешный результат содержит `status: "ok"`, `confidence` со значением
`medium` или `high` и объект `triplet_metrics`:

```json
{
  "triplet_score": 0.72,
  "profession_relevance": 0.81,
  "domain_similarity": 0.76,
  "mutual_similarity": 0.51
}
```

Пороговые значения по умолчанию:

- общий `triplet_score` — `0.55`;
- релевантность профессии — `0.45`;
- совпадение домена — `0.45`;
- взаимная близость — `0.20`.

Они настраиваются переменными `MIN_TRIPLET_SCORE`,
`MIN_TRIPLET_PROFESSION_RELEVANCE`, `MIN_TRIPLET_DOMAIN_SIMILARITY` и
`MIN_TRIPLET_MUTUAL_SIMILARITY`.

Если релевантных вакансий меньше трёх или лучший набор не проходит хотя бы
один порог, `run_pipeline` возвращает:

```json
{
  "status": "insufficient_market_data",
  "confidence": "low_confidence",
  "message": "Лучшая тройка не прошла пороги согласованности"
}
```

В этом случае группировка требований не вызывается и файл
`synthetic_vacancy.json` не создаётся и не перезаписывается.

Перед первым запуском загрузите embedding-модель:

```powershell
ollama pull bge-m3
```

Модель можно заменить через `OLLAMA_EMBEDDING_MODEL`. Доменный порог по
умолчанию равен `0.35` и настраивается через
`DOMAIN_SIMILARITY_THRESHOLD`. Если целевой профиль не содержит `domain`,
pipeline останавливается: безопасно применить жёсткий доменный фильтр в таком
случае невозможно.

Полное резюме не передаётся сайтам вакансий. В интернет уходят только
поисковые запросы. Тексты резюме и вакансий обрабатываются локальной Ollama.

Новые JSON используют `target_profession` в резюме и `profession` в вакансии.
Для совместимости pipeline продолжает читать старые строковые поля
`target_position` и `canonical_profession`, но при следующем сохранении выдаёт
новую структуру.

Для авторизованного hh.ru можно задать `HH_ACCESS_TOKEN`; идентификатор клиента
берётся из `HH_USER_AGENT`. Секреты не следует сохранять в репозитории.
